# Mono 空闲页归还：首轮实测（2026-09-30）

本轮使用独立只读采样器；VaM 进程、`mono.dll`、插件载荷及 GC/UUA 配置均保持原状。采样器绑定本机 `mono.dll` SHA256 `160F224EAD92DAC4F33E91A584FDC1C7EF82ED1CED2FEAC9A903AFA31A7E2738`，运行时还校对六段代码字节。源文件及验证见同目录 `MODIFIED_FILE.py`、`VERIFICATION.txt`。

## 已核对的内部路径

- `mono_gc_get_heap_size` 读取逻辑堆计数（RVA `0x27C7E0`）；空闲计数位于 `0x27C808`；未映射字节计数位于 `0x27EA88`。`monoHeap` 保持不变并不排除退页。
- GC 完成路径 `0x157EC4` 调空闲块扫描 `0x15FC90`。后者遍历 61 桶，检查 `gcNo−6` 与 header 状态；`0x15EB8C` 使用 `VirtualFree(..., MEM_DECOMMIT)`，重新使用时 `0x15EC50` 调 `VirtualAlloc(..., MEM_COMMIT)`。这两个路径对同一个未映射字节计数加减。
- `monoFree = heap−used` 包含已 decommit 的部分，不能直接当作仍可归还的提交量；`free−unmapped` 是已提交的大块空闲字节估计，仍非整页可退量。

## 年龄扫描的精度边界

三次外部遍历各到达约 5.29 万个空闲块，观察到 7985.64–7996.34 MiB；其中已退页 6660.32 MiB 与内部计数吻合。最后一次已观察部分：原年龄条件可退 **0 MiB**，假设 `6→2` 可退 **29.21 MiB**。遍历尾部有节点被游戏并发重新分配，三次报告均明确 `complete=false`、退出码 2；29.21 MiB 是观察部分的数，不是全堆精确收益，也不是修改阈值的依据。

**本轮判断**：第三层并非“没有退页”；现有退页已达约 6.50 GiB。剩余约 1.57 GiB 包含新近释放、持续复用和不足整页等空间。依据当前年龄扫描，调低年龄门槛尚没有数 GB 收益证据；先维持 native 条件，再在能同步观察完整空闲链表时核算其可退页量与下一轮 recommit 成本。
